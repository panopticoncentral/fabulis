# Fabulis UI review — September 17, 2026

Fabulis has a good native foundation. The biggest improvements would come from clearer navigation, more dependable editing, and a quieter reading experience. Keep SwiftUI and Mac Catalyst; give each platform an appropriate arrangement of the same features.

This is a comprehensive **source-level design and interaction review**, covering the current iOS and Mac Catalyst client, including uncommitted changes present during the review. All screen implementations and shared presentation components were inspected, along with navigation, app commands, relevant state handling, and existing UI tests. Apple design guidance was consulted. No application code was changed.

**Evidence limits:** I did not interact with a rendered, authenticated app on either platform. Installed iOS simulator runtimes were found, but no simulator was running. Findings below distinguish behavior visible in the source from design judgments and layout risks. Text clipping, actual hit areas, VoiceOver traversal, contrast, keyboard routing, animation quality, and OS-specific toolbar appearance still require runtime validation. This report is not a visual or accessibility certification.

The older April UI-refresh specification describes the retired Blazor interface. Its literary direction is useful background, but its light-only palette, web layout, and CSS are not requirements for this native client. The current implementation also supersedes some backlog descriptions: narration already has audio-session and system playback integration, and draft streaming already includes reconnection logic.

**What to preserve.** System colors, native forms and lists, SF Symbols, selection traits in pickers, selectable story text, the 720-point reading-column cap, initial-load retry views, explicit destructive confirmations, and preservation of the mounted library across authentication interruptions are all sensible choices. Existing New Draft, Settings, Save to Library, Refresh, and Lock shortcuts provide a useful start for the Mac. The shared one-liner/trope category implementation is a good precedent for reducing drift.

**Recommended order.** High means the issue affects the main workflow or confidence in the app. Medium means a noticeable usability or platform-fit improvement. Polish means visual refinement after the interaction model is settled. Effort estimates are relative implementation scope, not delivery promises.

**1. Library navigation needs a clearer hierarchy. High; both platforms; source-confirmed structure, design recommendation.**

The five types—Prompts, One-liners, Tropes, Drafts, Stories—occupy one segmented control above a category list. Every launch starts on Prompts. These are substantial destinations, and the long labels compete for limited sidebar/phone width. Five segments are not inherently against Apple's guidance; the problem is the combination of label lengths, available width, and the importance of the destinations. See [LibraryView](/Users/paulv/Projects/fabulis/client/Fabulis/Views/Library/LibraryView.swift:134) and [LibraryKind](/Users/paulv/Projects/fabulis/client/Fabulis/Views/Library/LibraryKind.swift:5). Apple's [segmented-control guidance](https://developer.apple.com/design/human-interface-guidelines/segmented-controls?changes=_4) emphasizes closely related choices and similar content sizes.

For iPhone, my preferred direction is three top-level destinations: **Drafts, Stories, and Resources**, with Prompts, One-liners, and Tropes inside Resources. This is a proposed information architecture, not a requirement; it assumes writing and reading are the main activities. For Mac, expose the same destinations as named sidebar items, with resource types grouped together. Preserve the selected category and item when moving between destinations.

On wider Mac/iPad layouts, consider a sidebar → item list → reader/editor arrangement, retaining the item list while a story is open. The current two-column split pushes the story into the category's detail stack, replacing its list. A third column is useful at adequate widths, not mandatory in every window. This follows Apple's guidance to consider an intermediate content list for deeper hierarchies in [sidebars](https://developer.apple.com/design/human-interface-guidelines/sidebars?changes=_11).

**2. New Draft should be available from the main browsing experience. High; especially iPhone; source-confirmed.**

The visible New Draft action appears only while Drafts is selected. On other types, its position becomes New Category. The Mac has Command-N, but the iPhone lacks an equally direct path to the central activity. Keep New Draft persistently available in the main library experience, while placing category creation within the relevant list/menu. Use an empty-state New Draft button as well. See [toolbarContent](/Users/paulv/Projects/fabulis/client/Fabulis/Views/Library/LibraryView.swift:98).

Prompts currently open an editor and cannot start a draft. The backlog explicitly acknowledges this feature gap. A visible **Use Prompt** or **Start Draft** action would make Resources feed the writing workflow, but it requires server work; do not treat it as a cosmetic change. See [PromptEditorView](/Users/paulv/Projects/fabulis/client/Fabulis/Views/Library/PromptEditorView.swift:37) and [BACKLOG.md](/Users/paulv/Projects/fabulis/BACKLOG.md:11).

**3. Preserve unsaved work when changing selection. High; both, especially Mac; source-confirmed state risk.**

Unsent draft text and edits live inside DraftView's local state. Selecting another draft replaces that view using `.id(id)`, and switching library type explicitly clears selection. There is no shared unsent-text store or navigation guard. Pushed prompt/storyteller editors guard their Back/Cancel path, but changing the surrounding sidebar selection can remove a detail subtree through a different path. See [DraftView state](/Users/paulv/Projects/fabulis/client/Fabulis/Views/Draft/DraftView.swift:14), [selection changes](/Users/paulv/Projects/fabulis/client/Fabulis/Views/Library/LibraryView.swift:45), and [detail identity](/Users/paulv/Projects/fabulis/client/Fabulis/Views/Library/LibraryView.swift:240).

Preserve unsent composition by draft ID for the active session. Use one dirty-editor policy for sidebar changes, Back, modal dismissal, and window closing. A protected editor should offer Save, Discard Changes, and Keep Editing as appropriate. Do not introduce plaintext disk persistence without separately resolving the vault's storage expectations.

**4. Discard protection differs between editors. High; both; source-confirmed.**

One-liner and trope sheets dismiss directly on Cancel and do not block interactive dismissal. Summary editing blocks interactive dismissal when dirty but its Cancel button immediately discards the edit. Prompt and storyteller editors have explicit discard confirmations. Users cannot predict which interactions preserve work. See [OneLinerEditSheet](/Users/paulv/Projects/fabulis/client/Fabulis/Views/Library/OneLinerEditSheet.swift:51), [TropeEditSheet](/Users/paulv/Projects/fabulis/client/Fabulis/Views/Library/TropeEditSheet.swift:50), [StorySummarySheet](/Users/paulv/Projects/fabulis/client/Fabulis/Views/Story/StorySummarySheet.swift:40), and [StorytellerEditorView](/Users/paulv/Projects/fabulis/client/Fabulis/Views/Settings/StorytellerEditorView.swift:94).

Use consistent change detection and dismissal handling. Leave unchanged editors easy to dismiss. Protect meaningful changed text, including the summary prompt in Settings. Apple's [sheet dismissal example](https://developer.apple.com/documentation/uikit/disabling-the-pull-down-gesture-for-a-sheet?changes=_4) demonstrates preserving unsaved changes through explicit save/discard choices.

**5. The composer needs separate compact and wide arrangements. High; both; source-confirmed layout, runtime fit unverified.**

The conversation is capped at 720 points, while the composer stretches across the entire detail width. On Mac this separates the typing position and send control from the reading column. During editing, the input shares one horizontal row with Cancel, Save, and potentially Resubmit. On a phone those controls compete directly with the editable text. See [inputBar](/Users/paulv/Projects/fabulis/client/Fabulis/Views/Draft/DraftView.swift:180) and [editButtons](/Users/paulv/Projects/fabulis/client/Fabulis/Views/Draft/DraftView.swift:284).

Align the composer with the reading column on wide layouts. On compact layouts, let the editor occupy a full row and put editing actions below it, or use one main action with secondary options. Give the composer a contextual label: Write a prompt, Edit prompt, or Edit response. It currently says Prompt even when editing a response. Consider an Expand Editor action for long revisions; the current custom field stops growing at five lines. See [SubmittableTextView](/Users/paulv/Projects/fabulis/client/Fabulis/Views/Draft/SubmittableTextView.swift:61).

**6. Opening an existing draft should not always summon the keyboard. Medium; iPhone; source-confirmed.**

`loadDraft()` sets focus to the composer for every draft. Opening an existing conversation to read it therefore requests the software keyboard. Focus immediately for a new empty draft or an explicit writing action; keep existing conversations in reading mode until the user chooses to type. Verify interactive keyboard dismissal and bottom anchoring together. See [loadDraft](/Users/paulv/Projects/fabulis/client/Fabulis/Views/Draft/DraftView.swift:303).

Hardware Return submits a prompt or saves an edit, while Shift-Return inserts a newline. This behavior is implemented in the shared UIKit view, not only on Mac. Keep it discoverable with a keyboard hint/help text and test iPad hardware keyboards. Plain Return is a reasonable chat convention, but long-form response editing should consider Return for newline and Command-Return for the explicit action, or a preference. See [key commands](/Users/paulv/Projects/fabulis/client/Fabulis/Views/Draft/SubmittableTextView.swift:206).

**7. Core message actions are hidden in context menus. High; both; source-confirmed.**

Editing, regeneration, and starting narration require long-press/right-click on a message. There is no visible starting Play action in the story toolbar, and the narration bar appears only once the player becomes visible. These are important features to leave undiscoverable. See [DraftView message menu](/Users/paulv/Projects/fabulis/client/Fabulis/Views/Draft/DraftView.swift:57), [StoryMessageView](/Users/paulv/Projects/fabulis/client/Fabulis/Views/Story/StoryMessageView.swift:43), and [StoryView toolbar](/Users/paulv/Projects/fabulis/client/Fabulis/Views/Story/StoryView.swift:68).

Add a visible Listen action to stories and a message action menu that is reachable without a hidden gesture. Keep context menus as a second route. On Mac, a quiet action affordance may appear on hover and keyboard focus; it still needs an accessible path when neither applies. On iPhone, use a persistent small menu button with a generous hit area.

**8. Destructive regeneration has two different warning paths. High; both; source-confirmed.**

Context-menu Regenerate confirms when later messages will be deleted. Editing a prompt and choosing Resubmit clears edit mode and calls the destructive resubmission path directly. A caption warns about editing consequences, but the action label does not describe replacing the continuation, and it bypasses the explicit confirmation used elsewhere. See [requestRegenerate](/Users/paulv/Projects/fabulis/client/Fabulis/Views/Draft/DraftView.swift:257), [resubmitEdit](/Users/paulv/Projects/fabulis/client/Fabulis/Views/Draft/DraftView.swift:392), and [editAndResubmit](/Users/paulv/Projects/fabulis/client/Fabulis/Views/Draft/DraftView.swift:402).

Use **Save Changes** for an edit that preserves the continuation and **Regenerate from Here** for replacement, with the same count-specific confirmation in both entry paths. Preserve the edit buffer until the operation succeeds. Rename “Delete and after” to “Delete from Here…” with an explicit explanation of which messages are removed.

**9. Distinguish editing from saving a story version. High; both; source-confirmed.**

The draft toolbar says Save and uses Command-S, but opens Save to Library. Inline editing also says Save. Selecting an existing story in the save sheet creates another saved version, yet the action still says Save. This obscures whether the user is preserving current text, creating a story, or adding a version. See [DraftView toolbar](/Users/paulv/Projects/fabulis/client/Fabulis/Views/Draft/DraftView.swift:144) and [SaveDraftSheet](/Users/paulv/Projects/fabulis/client/Fabulis/Views/Draft/SaveDraftSheet.swift:21).

Use **Save to Library…** for the toolbar/menu command. In the sheet, explicitly choose **New Story** or **New Version of Existing Story**, then show only the relevant fields. Use **Create Story** / **Save New Version** as the final button label. Replace decorative “— New category —” entries with “New Category…”. After success, show the saved destination/version and an Open Story action. Scope Command-S to the active editor when editing, and make its menu label match its actual operation.

The sheet also lacks category/story loading states; changing category leaves the previous story list in memory while fetching. A delayed category load sets the title after the user may have started typing, and generated titles replace the current title when the response arrives. Disable dependent controls during fetches, clear stale options, and avoid overwriting text that changed after a request began. See [sheet tasks](/Users/paulv/Projects/fabulis/client/Fabulis/Views/Draft/SaveDraftSheet.swift:82) and [loadStories](/Users/paulv/Projects/fabulis/client/Fabulis/Views/Draft/SaveDraftSheet.swift:106).

**10. Saved stories deserve a reading presentation. Medium; both; design recommendation.**

Drafts and saved stories use virtually identical PROMPT/RESPONSE cards, accent-tinted response backgrounds, uppercase role captions, and Markdown presentation. This is useful conversation context, but it makes the finished story feel like a transcript. See [DraftMessageView](/Users/paulv/Projects/fabulis/client/Fabulis/Views/Draft/DraftMessageView.swift:46) and [StoryMessageView](/Users/paulv/Projects/fabulis/client/Fabulis/Views/Story/StoryMessageView.swift:24).

Offer a **Read / Conversation** presentation switch for saved stories. Read should show the prose continuously, preserving paragraph and section structure, with prompts available in Conversation. Keep the existing width cap. Add a modest reading text-size control and consider a system serif option for prose. Keep navigation, buttons, and metadata in system UI typography. This would give Fabulis a literary identity without a large custom theme.

Unify shared message rendering so typography and accessibility fixes apply equally to drafts and conversation-mode stories. Avoid tinting every large paragraph container; reserve stronger emphasis for selection, editing, or playback.

**11. Toolbars need a stronger hierarchy. Medium; both; source-confirmed structure, runtime appearance unverified.**

StoryView puts Version, Share, Refresh, and Summary in trailing toolbar items. Category views have Refresh and Options, and prompt categories add a leading New Prompt button beside navigation. Mac can display both library and detail actions. See [StoryView toolbar](/Users/paulv/Projects/fabulis/client/Fabulis/Views/Story/StoryView.swift:68) and [PromptCategoryView toolbar](/Users/paulv/Projects/fabulis/client/Fabulis/Views/Library/PromptCategoryView.swift:88).

Prioritize the actions people use on the content. For a story, expose Listen and Share, make the selected version clear, and group secondary actions such as Refresh under More. Keep pull-to-refresh where supported on iOS. On Mac, provide an appropriately grouped window toolbar and menu commands; validate Catalyst's actual rendering before deciding whether a custom toolbar bridge is needed. Apple explicitly describes adapting iPad navigation-bar actions to a window toolbar in its [Catalyst toolbar tutorial](https://developer.apple.com/tutorials/mac-catalyst/adding-a-toolbar).

The Mac model subtitle currently consumes a separate full-width bar plus divider; older supported iOS versions omit it entirely. Move model information into a compact, consistent metadata location or an inspector/details view, with an older-iOS fallback. See [ModelSubtitle](/Users/paulv/Projects/fabulis/client/Fabulis/Views/Shared/ModelSubtitle.swift:12).

**12. Give Mac commands deliberate scope and discoverability. Medium; Mac; source-confirmed omissions, routing needs runtime testing.**

App-specific menu commands cover Settings, New Draft, and Lock Vault. Many content actions exist only inside views or context menus. Refresh declares Command-R independently in library and detail views; inline edit Save has no corresponding explicit shortcut. There are no custom help tooltips on the icon actions. See [FabulisApp](/Users/paulv/Projects/fabulis/client/Fabulis/FabulisApp.swift:15).

Add relevant content commands to File/Edit/View or an appropriate content menu: Save to Library, Rename, Delete, Listen, Summary, and navigation actions. Keep standard system editing commands. Route commands through the focused content so the visible menu, toolbar, and shortcut agree. Verify Command-R with sidebar versus detail focus rather than assuming the duplicate declarations choose the intended target. Add tooltips for icon-only controls and appropriate Escape/default-action behavior in sheets. Apple's [SwiftUI menu guidance](https://developer.apple.com/documentation/swiftui/building-and-customizing-the-menu-bar-with-swiftui) supports adding contextual app actions alongside system commands.

**13. Settings needs task-oriented organization and predictable saving. Medium; both; source-confirmed.**

Settings is one long Form: server, API key, narration connection/voice/speed, storyteller, summary model/prompt, auto-lock, and vault. It mixes immediate saves with explicit Save key, Save URL, and Save prompt buttons. A Done action can close the sheet with unsaved text. Success messages have different lifetimes, and errors appear at the end of the form, potentially far from the initiating control. See [SettingsView](/Users/paulv/Projects/fabulis/client/Fabulis/Views/Settings/SettingsView.swift:27).

Organize into **General**, **Writing**, **Narration**, and **Connection & Vault**. On iPhone, use a short settings index with focused detail pages; on Mac, use a bounded settings presentation with clear sections, ideally independently accessible from the app menu. Within a pane, use a consistent save policy: immediate changes for simple choices and explicit Apply/Save for longer text or connection details, with dirty-state protection. Put errors and pending/saved indicators beside their setting.

Show the current narration endpoint when the API can supply it, not just “Server URL is set.” Treat Lock Vault as a normal lock action rather than red destructive content deletion. Preserve the explicit destructive styling for actual deletion.

**14. Advanced writing settings are too exposed and too technical. Medium; both; design recommendation with source-confirmed validation issue.**

Storyteller settings show `top_p`, `max_tokens`, `min_p`, `top_k`, and `top_a` directly in the main form. Optional numeric text is parsed with Double/Int; invalid strings become nil, making a typo resemble an intentional unset value. See [sampling fields](/Users/paulv/Projects/fabulis/client/Fabulis/Views/Settings/StorytellerEditorView.swift:69) and [save parsing](/Users/paulv/Projects/fabulis/client/Fabulis/Views/Settings/StorytellerEditorView.swift:147).

Keep model, writing instructions, and a clearly explained creativity control easy to reach. Put detailed sampling under Advanced with human-readable names, technical identifiers as secondary help, explicit “Use model default,” and inline numeric validation. Use integer input for integer fields. The model picker should lead with the display name and put its API identifier second; the current hierarchy is reversed. Match the voice picker's row styling to the model picker's and give an empty voice result an explanatory state. See [ModelPickerView](/Users/paulv/Projects/fabulis/client/Fabulis/Views/Settings/ModelPickerView.swift:29) and [NarrationVoicePickerView](/Users/paulv/Projects/fabulis/client/Fabulis/Views/Settings/NarrationVoicePickerView.swift:17).

**15. Error and loading behavior should be consistent. High; both; source-confirmed.**

Library and text-item categories surface failed refreshes while retaining content. Story categories, prompt categories, and StoryView set load-error state, but their content-first branches hide those errors once content exists. A user can request a refresh, see no change, and receive no explanation. See [CategoryView](/Users/paulv/Projects/fabulis/client/Fabulis/Views/Library/CategoryView.swift:25), [PromptCategoryView](/Users/paulv/Projects/fabulis/client/Fabulis/Views/Library/PromptCategoryView.swift:30), [StoryView](/Users/paulv/Projects/fabulis/client/Fabulis/Views/Story/StoryView.swift:18), and the better distinction in [TextItemCategoryView.load](/Users/paulv/Projects/fabulis/client/Fabulis/Views/Library/TextItemCategoryView.swift:193).

Use one policy: initial load → loading then content/retry; refresh → keep content and show refreshing/retry feedback; action failure → explain the failed action without replacing content. Keep an error visible near its cause. “Something went wrong” is too generic as the default action title, while the one-liner/trope/prompt editors label load and delete failures “Couldn't save.” Supply operation-specific titles. See [ErrorPresentation](/Users/paulv/Projects/fabulis/client/Fabulis/Views/Shared/ErrorPresentation.swift:23).

Settings unlocks interaction after a failed initial fetch because `isLoading` becomes false even when `settings` is nil. Its default speed remains available and there is no explicit Retry screen. Keep data-dependent controls unavailable until data is loaded successfully. The draft initial-load failure is a dismissible bottom banner; dismissing it while `draft` remains nil exposes the loading placeholder again without initiating a retry. Give that case the standard load-failure/retry view. See [SettingsView.load](/Users/paulv/Projects/fabulis/client/Fabulis/Views/Settings/SettingsView.swift:184) and [draftPlaceholder](/Users/paulv/Projects/fabulis/client/Fabulis/Views/Draft/DraftView.swift:168).

**16. Search, naming, and sidebar updates need consistent state ownership. Medium; both; source-confirmed.**

One search string is retained across library-type switches, even though it changes from matching category names to matching draft titles. A user can move to Drafts and unexpectedly see an empty result caused by a category search. Drafts rendered as “Untitled draft” are filtered using an empty string for a nil title. Preserve a separate filter per destination or explicitly clear it on a type switch, and filter the displayed fallback title. See [LibraryView filters](/Users/paulv/Projects/fabulis/client/Fabulis/Views/Library/LibraryView.swift:21).

Renaming a category refreshes its detail but does not notify the library sidebar. Saving a prompt after moving it refreshes the prompt list but does not invoke the category-count callback used for create/delete. Refresh the shared library summaries after successful rename/move so both panes show the same names and counts. See [category rename callback](/Users/paulv/Projects/fabulis/client/Fabulis/Views/Library/CategoryView.swift:79) and [prompt save callback](/Users/paulv/Projects/fabulis/client/Fabulis/Views/Library/PromptCategoryView.swift:82).

Current search labels accurately say Filter, and most searches are title-only. Keep that honesty. Global content search would be useful, but it is additional functionality rather than a required label change.

**17. Shared categories need clearer consequences. Medium; both; design recommendation.**

Each library type presents the same categories with a count for that type. Deleting a category removes its stories, prompts, one-liners, and tropes, including content outside the current view. The existing confirmation correctly names all four types; preserve that warning. Strengthen it with the category name and available per-type counts, and consider “Delete Category and Contents…” at the entry point. Make the shared nature of categories visible in category management so it is not first discovered during deletion. See [LibraryCopy](/Users/paulv/Projects/fabulis/client/Fabulis/Views/Library/LibraryCopy.swift:6) and [CategoryRow](/Users/paulv/Projects/fabulis/client/Fabulis/Views/Library/CategoryRow.swift:16).

**18. Match editor presentation to task size and platform. Medium; both; source-confirmed presentation, runtime sizing unverified.**

Single-field category editing, short text-item editing, a long Settings form, and a summary reader all use broadly default sheet presentation. Summary puts Done in the cancellation slot while Settings puts it in confirmation. Prompt editing pushes a full form and uses an Edit button within an already named Edit Prompt screen. See [EditCategorySheet](/Users/paulv/Projects/fabulis/client/Fabulis/Views/Library/EditCategorySheet.swift:15), [StorySummarySheet toolbar](/Users/paulv/Projects/fabulis/client/Fabulis/Views/Story/StorySummarySheet.swift:40), and [PromptEditorView toolbar](/Users/paulv/Projects/fabulis/client/Fabulis/Views/Library/PromptEditorView.swift:66).

Use a compact, keyboard-aware sheet for category names; a larger expandable sheet for text items; and a full editor for long prompt sequences. On Mac, bound form width and choose appropriate sheet/window dimensions instead of relying entirely on phone defaults. Use consistent Cancel and confirmation placement for transactional sheets and a consistent Done convention for informational sheets. Rename the prompt's inner Edit mode to **Organize Messages** or give it explicit reorder/remove controls so it does not imply a second general editing state.

**19. Narration needs a more complete browsing experience. Medium; both; source-confirmed.**

Both StoryView and DraftView stop their local player on disappearance. Listening therefore ends when moving elsewhere in the library, even though system playback integration already exists. Promote playback ownership to a suitable shared scope if continued listening is desired, and retain a mini-player while browsing. Keep vault locking as a separate, explicit playback/privacy decision. See [StoryView lifecycle](/Users/paulv/Projects/fabulis/client/Fabulis/Views/Story/StoryView.swift:119), [DraftView lifecycle](/Users/paulv/Projects/fabulis/client/Fabulis/Views/Draft/DraftView.swift:155), and [NarrationPlayer](/Users/paulv/Projects/fabulis/client/Fabulis/Services/NarrationPlayer.swift:121).

The current player has useful skip controls, part count, and elapsed time. Improve it with a visible preparation label, access to playback speed, and a seek control when duration is known. On compact widths, reflow metadata below transport controls. In a draft, the player and composer should share a deliberate bottom-area layout. See [NarrationBar](/Users/paulv/Projects/fabulis/client/Fabulis/Views/Narration/NarrationBar.swift:25).

**20. Summary and generation states should explain what is happening. Medium; both; source-confirmed.**

An empty streaming response shows a small spinner and RESPONSE caption. Connection retries occur without a distinct reconnecting state. Use brief state labels such as Preparing response, Generating, Reconnecting, and Stopped, without exposing internal model reasoning. Provide a clear path to resume/retry after failure. The current completion accessibility announcement is a useful start; review failure and user-stop announcements too. See [DraftMessageView](/Users/paulv/Projects/fabulis/client/Fabulis/Views/Draft/DraftMessageView.swift:46) and [stream loop](/Users/paulv/Projects/fabulis/client/Fabulis/Views/Draft/DraftView.swift:430).

Summary tells users a missing or stale summary will appear/update automatically, but polling initially starts only for `generating`. A `none` or stale `ready` state can remain unchanged while the sheet stays open. Keep the promise synchronized with actual observation, or provide a Refresh/Generate action. Prefer retaining the previous summary with a regenerating indicator over replacing it entirely with a spinner. See [summary content](/Users/paulv/Projects/fabulis/client/Fabulis/Views/Story/StorySummarySheet.swift:83) and [startPollingIfNeeded](/Users/paulv/Projects/fabulis/client/Fabulis/Views/Story/StorySummarySheet.swift:187).

**21. Improve empty states, metadata, and authentication layout. Polish / Medium; both; source-confirmed, layout effects require testing.**

Empty states usually instruct people to find a toolbar action rather than including that action. The unselected detail says to read stories even when Prompts is the default destination. One-liner and trope empty states say “press Return,” which is a hardware-keyboard assumption. Use destination-specific descriptions with actual New Draft/New Category/Add actions, and neutral touch-friendly copy. See [LibraryView empty states](/Users/paulv/Projects/fabulis/client/Fabulis/Views/Library/LibraryView.swift:164) and [OneLinerCategoryView](/Users/paulv/Projects/fabulis/client/Fabulis/Views/Library/OneLinerCategoryView.swift:21).

Rows repeatedly use caption2 for counts and timestamps; draft timestamps include both date and time while story timestamps omit time. Define a shared row hierarchy: clear title, useful secondary detail, quieter date/count. Use contextual relative dates where useful and complete dates in details/help. Match unnamed draft titles between list and editor (“Untitled draft” versus “New Draft”). Test long imported-story titles together with their Imported label before choosing truncation or wrapping. See [DraftRow](/Users/paulv/Projects/fabulis/client/Fabulis/Views/Library/DraftRow.swift:7) and [story rows](/Users/paulv/Projects/fabulis/client/Fabulis/Views/Library/CategoryView.swift:34).

Onboarding is scrollable; unlock and server-unreachable screens use centered, non-scrollable vertical stacks. Long errors, a visible keyboard, or large text may make their actions difficult to reach. Reuse a responsive authentication shell with scrolling when needed. Keep a concise recovery message first, with technical details available separately. See [OnboardingView](/Users/paulv/Projects/fabulis/client/Fabulis/Views/Onboarding/OnboardingView.swift:13), [UnlockPromptView](/Users/paulv/Projects/fabulis/client/Fabulis/Views/Auth/UnlockPromptView.swift:13), and [ServerUnreachableView](/Users/paulv/Projects/fabulis/client/Fabulis/Views/Auth/ServerUnreachableView.swift:10).

**22. Accessibility needs a focused runtime pass, supported by a few source changes. Medium; both; risks, not measured failures.**

The main narration buttons explicitly allocate 44-point targets, while the close button, text-item Add control, error dismiss button, and composer Send control do not explicitly guarantee the same target. Native styles may expand some of these; measure the actual targets before declaring failures. Apply a shared minimum touch-area policy on iOS while preserving suitable Mac density. Apple's [UI design tips](https://developer.apple.com/design/tips/) recommend 44-by-44-point touch controls.

Give TextEditors explicit accessible field names; adjacent captions and section titles should not be assumed to provide the correct spoken label. Announce editing and currently playing states in addition to the accent border, and expose message actions to assistive technology.
